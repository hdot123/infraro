## 1. 一句话硬规则（所有者终裁原文）

> **公开消费项目走 GitHub-hosted runner，私有消费项目走私有 self-hosted runner；所有消费项目都通过 scheduler 白名单获得 infraro-core 引擎使用资格，但公开项目不接触自建 Runner。**

## 2. 硬规则十条（所有者终裁原文转录）

1. 声明层 infraro 可以公开
2. scheduler 私有，作为引擎消费白名单和对账中心
3. infraro-core 私有，负责引擎和最终守卫
4. 公开消费仓库只能使用 GitHub-hosted runner
5. 公开消费仓库与任何自建 Runner、runner-hub 完全无关
6. 私有消费仓库才允许使用私有 self-hosted Runner
7. 公开或私有消费项目都必须先登记到 scheduler，否则不能使用引擎层
8. 仓库私有权限、scheduler 白名单、Runner 类型是三套独立控制
9. 公开消费项目不能持有 infraro-core 的长期 PAT、scheduler Token 或 Runner 凭据
10. infraro-core 必须在入口再次验证消费项目授权状态

### 2.1 公开消费项目十条硬性规则（原文转录）

1. 只能 GitHub-hosted runner
2. 不得用 self-hosted runner
3. 不得用 runner-hub
4. 不得访问私有 Runner 网络
5. 不得持有 infraro-core 仓 PAT
6. 不得持有 scheduler token
7. 不得直接 checkout 私有 infraro-core
8. 不得读取其他消费项目 Secret/Artifact/日志
9. 必须经 scheduler 白名单
10. 必须 infraro-core 入口再校验

**执行语法要求**：公开项目 workflow 必须 `runs-on: ubuntu-latest`（禁止 `self-hosted` / `[self-hosted, pve-linux]`）。

### 2.2 私有项目规则（原文转录）

- 项目 A 用独立私有 Runner 注册，不与公开仓共用
- 未来多私有项目可按信任域共享 `private-standard-pool`，但该池**永不服务公开项目**
- 私有仓也不因「私有」就完全信任 PR workflow（GitHub 官方安全提醒）

### 2.3 三套独立控制（不可混淆，原文转录）

| 控制面 | 管什么 |
|--------|--------|
| scheduler 白名单 | 是否允许使用引擎 |
| Runner 类型 | 哪类执行环境 |
| GitHub 仓库权限 | 能否访问私有源码/Action/Workflow/制品 |

三者不可互相替代、不可混淆。

### 2.4 runner-hub 定位收窄（原文转录）

- 只服务私有信任域或高敏感任务
- 不管公开消费项目
- 不给公开仓提供 runner
- 不代 scheduler 授权
- 不代 infraro-core 守卫

## 3. 四组件职责表

四个组件构成声明、授权、引擎、执行管理四个层面：

### 3.1 infraro（声明层）

| 维度 | 内容 |
|------|------|
| 负责 | 声明层协议/Schema（硬规则 #1）；公开声明资料；作为公开消费项目的协议接入门面 |
| 不负责 | 授权判定（scheduler 职责）；引擎实现与守卫（infraro-core 职责）；提供任何 runner；代持任何凭据 |
| 可公开 | 是（「声明层 infraro 可以公开」，硬规则 #1） |
| 不可公开 | 无——按裁定其定位即公开声明层 |

### 3.2 scheduler（授权平面）

| 维度 | 内容 |
|------|------|
| 负责 | 引擎消费白名单（公开/私有消费项目获得引擎使用资格的唯一登记入口，硬规则 #2/#7）；对账中心 |
| 不负责 | 提供执行环境；代 infraro-core 做入口守卫；管理 runner-hub；向公开项目分发任何 token |
| 可公开 | 否（「scheduler 私有」，硬规则 #2） |
| 不可公开 | 白名单数据、对账逻辑、内部凭据 |

### 3.3 infraro-core（引擎层）

| 维度 | 内容 |
|------|------|
| 负责 | 引擎本体；最终守卫——入口再次验证消费项目授权状态（硬规则 #3/#10） |
| 不负责 | 授权登记（scheduler）；公开声明协议（infraro）；给公开仓提供 runner 或网络可达性（公开十条 #3/#4） |
| 可公开 | 否（「infraro-core 私有」，硬规则 #3）——**注意：此为 v2 目标态，现行仓库仍为公开交付面，定位变更属草案状态，见第 6 章** |
| 不可公开 | 引擎源码、入口守卫逻辑、授权校验实现 |

### 3.4 runner-hub（执行管理面）

| 维度 | 内容 |
|------|------|
| 负责 | 只服务私有信任域或高敏感任务 |
| 不负责 | 公开消费项目（不管、不提供 runner）；代 scheduler 授权；代 infraro-core 守卫 |
| 可公开 | 否（私有） |
| 不可公开 | dispatch 面、任务数据、内部凭据 |

### 3.5 组件关系图

```
公开消费项目（PUBLIC 仓库）
    │ 经 infraro 声明协议接入 → GitHub-hosted runner 执行
    │ （零长期凭据；与自建 Runner、runner-hub 完全无关）
私有消费项目（PRIVATE 仓库）
    │ 同样必须先登记 scheduler 白名单
    │ → 私有 self-hosted Runner（独立注册，不与公开仓共用）
    ▼
infraro（公开声明层）── 定义 Schema/协议，接收声明请求
scheduler（私有授权平面）── 引擎消费白名单（唯一登记入口）＋ 对账中心
infraro-core（私有引擎层）── 引擎本体 ＋ 最终守卫（入口再校验）
runner-hub（私有执行管理面）── 只服务私有信任域或高敏感任务
```

## 4. 代理链否决依据（「infraro 认证代理调用引擎」为何不采纳）

历史提案曾主张一条认证代理链：消费项目向 infraro 发声明请求 → infraro 代表消费项目认证调用引擎 → 引擎任务集中受控执行。该形态经对抗审查与终审核验后**不采纳**，所有者终裁（v2）确认不复活。

### 4.1 两条不可能路径（终审裁决原文）

在 GitHub Actions 的 thin-caller 加 pip 安装交付模型下，「infraro 代表消费项目认证调用私有引擎」这一代理链形态只有两种实现方式，**两条都不可能**：

1. **给消费方分发凭证——复活已列为不迁移项的 token 链**。公开消费项目不得持有任何长期凭据（硬规则 #9、公开十条 #5/#6），分发凭证即重建已否决的 token 信任链。
2. **由 infraro 转发引擎内容——构成 BOUNDARY 明文 Denied 的中间转发层**。本仓 [BOUNDARY.md](BOUNDARY.md) 将 Proxy Packages（代理包）、Forwarding Packages（转发包）、Internal Gateways（内部网关）列为 Denied 项，infraro 作为转发层直接违反该裁定。

两条独立审查路线对该结论一致，终审独立核验后认可成立。用户提案中的三层心智模型（声明、引擎、执行）予以采纳并落实为第 3 章的四组件职责表；被否决的仅是「认证代理调用」这一连接形态。

### 4.2 v2 终裁后的替代形态

代理链不复活，公开项目触达引擎的受控机制改为：**经声明协议 + 短时凭证受控引擎入口**。不放长期 PAT 进公开仓，候选机制（所有者裁定列出）：

- GitHub App
- 短时安装 Token
- OIDC 换短时凭证
- 私有 Package Registry
- 私有 reusable workflow
- 私有 API

若用私有 Action / reusable workflow，被调仓须显式配置访问策略，注意外部协作者间接接触风险。

## 5. 公开/私有双路径分离

所有者裁定将执行路径按消费项目可见性彻底分离：

| 路径 | 执行环境 | 凭据 | 与 runner-hub 关系 |
|------|----------|------|--------------------|
| 公开消费项目 | GitHub-hosted runner（`ubuntu-latest`） | 零长期凭据（短时受控凭证触达引擎） | 完全无关 |
| 私有消费项目 | 私有 self-hosted Runner（独立注册） | 私有信任域内部管理 | 可按信任域服务 |

两类项目都必须先登记 scheduler 白名单才能使用引擎层（硬规则 #7，一视同仁）。

## 6. 引擎定位变更（草案，flip 前不生效）

> **本整章为草案状态：flip 门禁未通过前不生效。生效前，infraro-core 现行形态仍为公开交付面，本仓一切安装指引、模板锚点、匿名拉取基线照旧执行。**

| 维度 | 现行（生效中） | 目标（草案） |
|------|----------------|--------------|
| 引擎定位 | 公开交付面：源码公开是已接受的成本，git+https 匿名可拉 | 私有实现 + 受控交付 |
| 公开交付承担 | infraro-core 仓库自身即交付面 | 官方制品与 infraro（声明层）承担公开交付 |
| 生效条件 | — | 治理包三件套（D1 定位变更 + BOUNDARY「官方发布渠道」修订 + 门 #5′）一起提交、一起审批通过，且 flip 完成后 |

变更要点（草案内容，均以治理包审批与 flip 为前提）：

- **D1 定位变更**：引擎定位从「公开交付面」变更为「私有实现 + 官方制品与 infraro 承担公开交付」。
- **BOUNDARY 修订**：新增「官方发布渠道」定义——引擎 CI 直接产出、单一上游、全自动；第三方转包和镜像仍为 Denied。
- **门 #5′**：验收对象从「引擎仓 git URL 匿名可拉」改为「官方制品匿名可拉」，「无 token 匿名安装成功」断言不变。
- **三件套联动**：任一项被否决则全部不生效，不得拆分单独立项。
- **flip 顺序约束**：registry/通道就绪 → 切模板 → 消费 CI 转绿 → 最后 flip，不可倒置；flip 前保留紧急通道，并配三级回滚预案。

## 7. 遗留设计点（待所有者裁定，本文不替所有者决定）

1. **infraro / scheduler 自身 CI 的 runner 归属**：infraro 是公开仓，按硬规则它自己是否可用 self-hosted runner，还是算「内部仓」豁免，待所有者裁定。
2. **GitHub-hosted runner 的 Actions 分钟费成本**：公开消费项目 CI 从自建池迁到 hosted 的费用影响，待所有者知晓权衡后裁定。
3. **现存迁移盘点**：历史 workflow 中残留的 self-hosted 引用与迁移注释的清查处置方式，待盘点结论回报后裁定。
